MacCrab v1.22.0

This release makes MacCrab honest about its own state, and fixes the reasons it
could go quiet without saying so.

Stability

- Fixed a crash on the enrichment timeout path that could terminate the engine
  under memory pressure. The engine restarted automatically, so the only visible
  symptom was a silent gap in coverage.
- Event storage now reclaims space it has already freed. A store could hold
  hundreds of megabytes of reusable free space, count it against its own size
  limit, pause writes, and shed new events while doing so.
- Reading recent events no longer rebuilds the whole event index whenever older
  events expire. On busy machines this made the dashboard expensive to leave
  open.
- Fixed expired event storage never being reclaimed. The sweep that removes
  aged event blocks treated two documented-transient conditions as failures and
  gave up for the rest of its pass, then met the same conditions on its next
  one. On a machine running a few hours, 86% of stored events were past their
  retention deadline and still being read on every query. Because every event
  lookup pays for the blocks that remain, this also made the dashboard steadily
  more expensive the longer the engine ran.

Alerting

- Fixed the notification channel not starting when MacCrab launches without its
  window open, which is the normal case for a menu-bar app. Affected installs
  posted no alert banners at all.
- A large backlog of pending alerts now drains steadily instead of arriving as
  one burst.
- Notification delivery reports what it is doing. A channel that is silent while
  alerts are waiting now says so in the log.

Prevention

- Network blocking now reports whether it is actually in effect. MacCrab writes
  rules into a packet-filter anchor, but macOS evaluates that anchor only when
  the packet filter is enabled and the anchor is registered in the system
  ruleset. MacCrab configures neither, and `pfctl` reports success regardless —
  so blocks were reported that could not occur. Every affected surface, and the
  documentation, now states this plainly. This corrects the reporting; it does
  not change what was being enforced.

Evidence

- `maccrabctl trace export` works again. It was opening the causal-graph store
  without a read key, so no trace bundle could be exported — including from the
  dashboard's Export button, which uses the same command.

Diagnostics

- Collector health distinguishes "not started" from "running and quiet". Two
  collectors that never start on a standard install previously reported healthy.
- Every collector now reports why it is in its current state.
- Event storage maintenance now reports its own health. It was measured
  internally and never published, so a sweep that gave up on every pass was
  invisible.
- Maintenance messages are recorded at a level macOS keeps. They were written at
  a level the system does not persist to disk, so they could not be read back
  after the fact.
- The AI backend now records why it is on or off at startup. Previously these
  messages went to standard output, which release builds discard, so an
  operator whose configured backend failed to load had no way to find out why.
- Rule-reload confirmations are visible on release builds. The message
  confirming a reload took effect went to standard output and was discarded, so
  the only signal that reloading worked could not be seen.

Minimum macOS 13.0.
